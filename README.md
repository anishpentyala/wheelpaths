# wheelpaths

Plan collisions in the destinations of a chosen set of Python wheels, without
installing them or importing their code. Supply an explicit POSIX installation
scheme. The output binds every claim to the SHA256 of the exact archive snapshot
read for the plan and distinguishes archive members from generated entry-point
scripts.

This is a path planner, not a package resolver, wheel validator or safe-install
certificate. `NO_COLLISIONS_IN_MODEL` means exactly that. It does not mean the
packages can be used together or installed safely.

## Run

Install from this repository with `pip install .`, then:

```sh
wheelpaths --scheme scheme.json first.whl second.whl > plan.json
```

`scheme.json` must have exactly these four keys, with canonical absolute POSIX
paths. Equal destinations are allowed and important:

```json
{
  "purelib": "/venv/lib/python3.12/site-packages",
  "platlib": "/venv/lib/python3.12/site-packages",
  "scripts": "/venv/bin",
  "data": "/venv"
}
```

Exit 0: no collision found in the supported model. Exit 1: collisions found.
Exit 2: invalid/unsupported input, never a clear plan. Argument syntax errors use
argparse's stderr and exit 2; data/input errors produce JSON with status INVALID.

Root members use `Root-Is-Purelib`. Members in the wheel's own `.data/purelib`,
`.data/platlib`, `.data/scripts` and `.data/data` are relocated. `console_scripts`
and `gui_scripts` create POSIX command-name claims. Other entry-point groups
are ignored, including misspelled script group names; they do not generate
commands in this model. Equal targets are conflicts
even with equal contents: two owners can remove each other's files on uninstall.
A file that another claim needs as a directory is also a conflict. Shared
directories alone, including namespace-package directories, are not conflicts.

Archives are never extracted. At most 256 MiB of archive bytes, 100,000 members,
and 1 MiB per read metadata file are accepted. This is not a general hostile-input
sandbox or a resource bound on total invocation size.

## Supported boundary

- Metadata ZIP compression must be stored or deflated; corrupted reads are INVALID.
- Wheel-Version 1.0, one expected `.dist-info` directory, optional matching `.data`.
- Explicit exact, case-sensitive POSIX lexical paths only.
- Candidate wheel set only; no network and no installed environment inspection.
- Headers and unknown schemes, special/symlink ZIP entries, duplicate members,
  traversal/noncanonical paths and unknown metadata layouts fail explicitly.
- Root metadata identity is checked against the filename. RECORD contents,
  member payload checksums, dependency metadata and wheel validity are not checked.

Not modeled: existing files, filesystem symlinks, case/Unicode aliases, Windows
launchers, generated bytecode, installer-added metadata such as INSTALLER, import
shadowing, ABI/tag compatibility, package dependencies or execution safety. The
scheme must reflect the intended install layout; it is not inferred from the
machine running the planner. No guarantee about a specific installer's extra
files or behavior is implied. No source builds or editable installs.

## Checked example

An offline plan for actual `jwt 1.4.0` and `PyJWT 2.15.1` wheels finds four shared
destinations: `jwt/__init__.py`, `jwt/exceptions.py`, `jwt/py.typed` and
`jwt/utils.py`. The archive URLs and hashes are in `evidence/downloads.json`.
In a disposable staging directory, pypa installer copied the first wheel's 14
projected paths and refused the second wheel at the first predicted collision.
This is local verification, not maintainer adoption. The packages were not imported.

The test suite also checks `.data` relocation, aliased/distinct scheme roots,
console/gui scripts, within-wheel projection collisions, file/directory clashes,
namespace-directory sharing, invalid metadata, duplicate members, special files,
and machine-readable CLI outcomes. See `evidence/QUALIFICATION.md` for exact
runtime, negative-control and installed-artifact scope.

## Existing work and intended use

Conflict detection is not new. ModuleGuard already studies and detects import
module conflicts. check-wheel-contents checks individual wheel contents.
Installer and package-manager overwrite checks are useful at install time.
wheelpaths instead emits an explicit, offline, cross-archive destination plan
including non-module `.data` and generated command targets. It is a small CI or
release-preflight building block, not a replacement for those tools. The research
notes cite their actual capabilities and do not claim exhaustive novelty.
